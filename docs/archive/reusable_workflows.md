# 可复用工作流

## 工作流 A：项目上下文盘点 → 小步实现 → 证据交付

适用：任何涉及代码、数据模型、依赖、生成文件或跨模块修改的请求。

1. 读取 `AGENTS.md`/`CLAUDE.md`、`README.md`、`docs/PROJECT_MAP.md` 和当前 `git status`。
2. 用 `rg` 定位数据模型、入口、provider、测试和已有实现；先画出数据流，再决定改动点。
3. 把需求写成 3 个以内的可验证验收条件，明确不在范围内的内容。
4. 优先修改纯 Dart policy/service，再接 UI；每次只完成一个垂直切片。
5. 添加针对性回归测试；模型或 provider 变更后运行 `dart run build_runner build --delete-conflicting-outputs`。
6. 运行 `flutter analyze` 和相关 `flutter test`，必要时再跑全量测试。
7. 最终只报告实际完成的文件、命令输出和剩余风险；不把计划、承诺或模型猜测写成完成事实。

完成条件：代码、测试、生成文件和用户可见结果四者都能被定位。

## 工作流 B：显式工作模式文件交付

适用：用户要求“生成/修改/写入/导出文件”或明确要求使用工具。

1. 从用户请求提取目标文件路径、格式、内容边界和验证方式；缺少文件名时主动指定合理文件名。
2. 判断是否进入显式工作模式，选择一个有能力且被点名的执行角色。
3. 调用 bridge health check；连接失败时立即返回启动命令、失败原因和重试条件。
4. 读取最小必要上下文，生成完整文件内容；不在聊天中用代码块冒充文件交付。
5. 写入前等待需要的批准；写入工具返回失败时保存 `waitingForApproval`/`failed` 状态，禁止继续声称完成。
6. 写入成功后验证：文件存在、路径在允许工作区内、字节数大于 0、关键内容可读取；需要时运行格式化/测试。
7. 回传“已生成 + 项目相对路径 + 验证证据 + 未完成项”，并把任务状态置为 `completed`。

禁止：只说“马上”“正在做”“已经推了”；重复写入同一文件；把 bridge 失败包装成自然闲聊；把工具返回空 stdout 当成文件验证。

## 工作流 C：自动群聊质量回放

适用：调整自动聊天、回复资格、人格化 prompt、关系记忆或主题场景。

1. 选择一段真实归档作为固定回放样本，记录消息数、AI/用户比例和主题。
2. 统计规范化正文的 exact duplicate、连续同角色回复、相同模板开场和无信息增量。
3. 明确回复规则：提及优先级、最近说话冷却、话题相关性、关系动作和重复预算。
4. 先为 policy 和 prompt builder 写纯逻辑测试，再接真实页面或 mock provider。
5. 用同一回放样本验证：重复文本下降、对话仍继续、被点名角色能响应、自动聊天能按预算暂停。
6. 检查成本和记忆更新频率，避免为了“更像真人”无限增加模型调用。

完成条件：既有可读的回放差异，也有测试能阻止重复问题回归。

## 工作流 D：对话归档与问题复盘

适用：用户要求归档全部聊天、总结做得不好的地方、提炼 Skill 或检查重复请求。

1. 先确认数据源和 debug/release 路径，复制数据或只读打开，不改原 Hive。
2. 运行 `dart run tool/archive_conversations.dart`，生成索引、JSON 和逐对话 Markdown。
3. 先看全局统计，再按对话查看高密度样本；分别统计用户重复和 AI 重复。
4. 用“路由、执行、可见性、上下文、风格、事实、生成质量、范围漂移”分类问题。
5. 为每条问题写证据、根因假设、优先级和退出条件；区分产品缺陷、测试数据行为和用户反复施压。
6. 把稳定做法写入 Skill，把一次性修复写入 review 报告；不复制相同规则到多个文档。
7. 重新运行归档脚本并校验 JSON、文件数、链接和隐私字段后交付。
