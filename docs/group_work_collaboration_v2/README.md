# 群聊工作模式：协作、验收与持续修订 v2

日期：2026-09-30。状态：**设计与实施提示词已编写，尚未实施**。

本方案来自本次 17 轮需求访谈及后续发言质量补充。目标是让已有群成员围绕真实任务讨论、查证、制作和验收，形成可恢复、可追溯的协作闭环。适用于所有群聊工作模式任务；软件开发必须包含需求梳理、技术确认、开发、测试、返工与复测。

1. [产品与技术设计、验收矩阵](01-design.md)。
2. [源码事实、GitHub 对照与分阶段计划](02-evidence-and-plan.md)。

每个阶段的提示词可以单独复制给 Codex；提示词会要求先读取本目录的设计与实施约束。按 P1 → P8 顺序实施，阶段内完成修改、检查与修复后再进入下一阶段。本次不提供供产品直接使用的整套角色系统提示词，但实施阶段必须修改实际生产提示词和协议，以支持新流程。

本目录取代 `docs/group_work_discussion/` 中与以下已确认决定冲突的产品规则；旧目录保留为历史实现记录。其他安全、权限、数据保护规则继续遵守仓库 `CLAUDE.md`。这不是让开发工具忽略旧实现，而是明确哪些行为需要有意迁移。

## 已确认决定

| ID | 用户选择 | 落地约束 |
|---|---|---|
| D01 | 开工前确认完整方案 | 解决当前所有已知疑问后才正式制作；允许先读取资料查证，不默认先做原型。执行中新发现的问题回到讨论。 |
| D02 | 团队自主决定开工 | 根据方案、问题清单和验收标准决定；用户偏好、范围取舍分歧或团队无法解决的问题才找用户。 |
| D03 | 全员认可后交付 | 当前工作团队每位成员必须明确认可，不能改成负责人独自批准或多数票。 |
| D04 | 异议必须有依据 | 关联目标、需求或质量要求，并给出具体问题、依据和可验证的解决条件；无法统一的新想法弹窗裁决。 |
| D05 | 一致同意的新想法可加入 | 即使超出原有范围，只要工作团队一致同意，也可纳入并更新需求、测试和计划；不得覆盖用户明确禁止事项或新增工具授权。 |
| D06 | 取消群任务累计限制 | 取消累计 100 步与任务总时长限制；持续有进展就继续，反复失败、持续无进展或无法解决的阻塞才求助。 |
| D07 | 弹窗可输入建议 | 用户可以解释、纠正、提供替代方案，团队收到后继续；不能只有重试／停止按钮。 |
| D08 | 暂缓后继续，最后再提醒 | 用户让某项先放着时，保留待办并推进不依赖的工作；其他工作完成后再次弹窗，不能把“继续”视为豁免或验收通过。 |
| D09 | 只选相关成员参与 | 从当前群选择相关工作团队；其他成员可补充意见，不强制凑数发言或承担签字责任。 |
| D10 | 所有任务；软件有必经流程 | 文档、调研、设计等使用对应审查；软件交付必须经过完整开发测试闭环。 |
| D11 | 人格影响表达与关注点 | 性格、职业、心情、关系可以影响措辞和讨论习惯，不能降低职责、事实或验收标准。 |
| D12 | 每轮保留交付版本 | 每轮送测／修订留存可打开的文件版本，关联修改说明、测试结果和未决问题；最终标记验收通过版本。 |
| D13 | 经验可跨项目复用 | 已验证通用经验和稳定用户偏好可跨项目；项目事实保持项目边界，历史经验不等于本次证据。 |
| D14 | 执行中及时纳入补充 | 即时确认收到，在安全检查点处理；必要时回到讨论并更新实现和测试，保留成果、不丢输入。 |
| D15 | 本地持久执行 | 切群／切页面继续；退出 App 后不继续生成，下次打开核对现场后自动恢复可执行工作。 |
| D16 | 缺角色由用户确认补充 | 从已有角色库推荐，由用户确认加入本次任务；无合适人选时用户补角色或承担对应验收。 |
| D17 | 交付实施提示词 | 给 Codex 等开发工具的分阶段仓库改造提示词，不单独交付一套产品运行时角色提示词。 |
| D18 | 发言必须像真实同事讨论 | 简短、具体、接住他人的问题，有角色差异；消除冗长职业报告和重复背景。覆盖讨论与测试返工全过程，以连续真实群聊样本验收，不能只隐藏长文本。 |

## 实施约束（每个阶段都适用）

- 开始前完整阅读仓库 `CLAUDE.md`，遵守中文回复、全部红线、死循环防护和完整校验规则。
- 先检查 `git status --short`，沿实际调用链阅读相关实现与全部调用方。不得覆盖、还原或擅自提交已有改动。
- 本次调研基线为 HEAD `b3b7921d6df2ff87b5519bf357aa8c0047f46a9a` **加当时未提交的工作树**；实施时以新工作树为准，行号只作定位。
- 复用 `WorkTaskCoordinator`、`WorkAgentLoop`、现有工具、角色、记忆、审批、文件交付和事件机制。禁止建立第二执行引擎、通用工作流平台、新角色人格体系或新数据库。
- 仅群聊工作模式启用 v2；普通聊天、私聊和现有命令权限边界不随之改变。工作模式仍不运行无关闲聊。
- 新业务规则必须进入生产调用链，不能只改未被调用的帮助方法或提示词。特别核查 `buildAgentDecisionPrompt`、记忆 wrapper 和讨论入口。
- 取消累计限制时，必须同时有检查点、取消能力和无进展保护。单次请求／工具超时、有限错误重试、上下文窗口、文件体积及全局并发保护不是累计任务限制，不得一起删除。
- P1–P7 构建并验证 v2 路径，默认群入口暂不创建 v2 状态；P8 完成整体验证后统一切换。用明确的状态版本区分，不新增面向用户的实验开关，不让两个执行循环同时消费同一任务。
- 任何 Hive／JsonSerializable 模型改动后运行代码生成，不手工改 `*.g.dart`。保持字段编号、未知版本处理和旧记录迁移兼容。
- 使用仓库现有测试设施；增加能捕捉真实回归的最小必要测试。不新增测试框架，不把文字匹配当作闭环验收。
- Flutter 测试每个用例严格 30 秒；涉及 Hive 的 widget 测试及 AppToast 遵守 `CLAUDE.md`。使用假时钟和受控工具模拟长任务，不真实等待 60 分钟或调用收费模型做常规回归。
- 每阶段开始先定校验范围，完整收集范围内问题再集中修复／报告。至少检查需求、正确性、边界／失败、有效测试、安全、性能、可读性、架构、旧数据兼容及仓库质量清单。
- 阶段结果必须写明修改、执行命令、通过／失败／未检查项和原因。阻塞时不得宣称通过；不要只报第一个问题，也不要为了凑全量反复运行已通过且未受影响的检查。
- 安全红线只维护在 `CLAUDE.md`；本目录描述本需求的业务与实现方案，不向 `AGENTS.md` 复制规则。
- 未授权的发布、推送、安装、访问真实私人历史／凭据不属于本次实施提示词的默认动作。常规实现与必要验证无需逐步重复请求确认。
