# P7 — 实际制作、测试、返工和全员认可闭环

日期：2026-10-01。仅实施 P7。已完整阅读 CLAUDE.md、本目录 README、设计、证据计划及 P1–P6，追踪 coordinator 的提交、调度、执行、讨论、恢复以及 runner/loop/文件交付的全部完成分支。保留开始时已有的暂存、未暂存及未跟踪修改；没有提交、推送、安装依赖、读取私人历史或真实凭据，没有默认创建生产群 v2 状态。恢复迁移、跨设备重验、真实模型自然性与入口启用仍由 P8 负责。

## 实际生产接线与状态权威

一根 `AgentTask` 贯穿用户目标。`WorkTaskCoordinator` 通过现有 runner 的 `prepareCollaborationWork` 在资源规划前选择本轮责任人；`DefaultWorkTaskRunner.execute` 复用唯一 `WorkAgentLoop` 执行材料、制作、修复和工具审查。P4 的 `WorkDiscussionRunner` 继续逐个请求真实成员讨论及认可，不承接制作工具循环。没有新增执行引擎、数据库或角色。

`executionStateJson.discussionState.collaboration` 是唯一业务记录。根级 `workItemExecution` 只绑定当前 actor/stage/workItem/iteration/requestRevision/teamRevision/verificationRevision，并隔离工具重试，不能自行推进方案。旧 `WorkHandoffState` 不参与 v2 调度，不向下一成员注入上一成员的 handoff 身份。旧任务的 handoff 路径保留兼容；没有通过删除 early return 启用双状态推进。

P4 就绪方案必须明确工作项、依赖、验收、文件合同。软件还需需求/技术/测试材料工作项、实现工作项和明确的验证命令。缺合同回 P3，不能写一个 HTML 就宣称整个目标完成。其他任务按产物合同走正文、格式和专业审查；只要软件需求文档仍是文档任务。

切换工作项前先保存完整结果与交接依据（事件详情文件、工作项 resultRef、下一职责、版本），发真实责任成员的简短交接消息，再排队。旧审批、待执行工具、角色上下文摘要、临时审查回执和旧失败被清理；目标文件、提交过的操作记录与会话所有权保留。coordinator 的 lease 在 finally 释放后才继续排队，下一 actor 重取必要锁；没有绕过原并发上限或同会话所有权。缺显式锁的 v2 工作区使用现有树写锁，保守串行保护制作及运行验证。

实际请求重新解析当前成员模型配置、凭据、责任资格、技能、人格/记忆和工具权限。负责人只收敛方案，不替所有人执行。审查者不允许是候选制作者或本轮任意主要实现工作项的责任人；软件还需合格测试责任。缺能力通过 P3/D16 推荐已有成员，或用户明确承担对应审查，不创造成员。快速答复缺人决策后必须结束旧讨论轮，新会话先应用已确认的成员，避免旧团队直接继续。

## 候选、工具证据与返工

制作工作项完成后调用 P6 `publishCandidate`，合同文件成为 rNNN 冻结版本，首次送测附真实可打开文件。材料完成不等于候选完成，候选完成不等于验收完成。审查前后校验冻结文件、工作区被测文件与摘要，真实工具回执由 loop 的结果观察点收集，不能从模型总结推断工具成功。

软件命令必须与已确认 verificationCommands 的 executable/arguments 相符；测试脚本必须属于候选合同。审查阶段禁止 workspace.patch 等制作副作用，命令运行前后仍校验候选及测试文件。工具幂等键加入 task/stage/workItem/iteration/requestRevision/verificationRevision：同轮重试不重放提交副作用，下一候选、合法修复或同候选新验证基线使用新键。回执详情在现有 eventStore 落盘并与 committed key 一起检查点保存；恢复时核对绑定与摘要，旧回执不能冒充本轮执行。

软件工具输出须明确候选摘要和逐验收用例结果（id/status/method/reproduction/expected/actual）；stdout 截断、退出码 0 但覆盖缺失都不能通过。模型审查结论还需完整方法、报告、验收引用和全部缺陷。实际失败不能被结论省略，失败报告必须记录复现、预期、实际、关联验收和复测条件。HTML 标签、能打开或静态文件守卫不构成交互验证。

报告使用 P6 start/report 文件记录方法、实际 actor、候选版本、验证版本、工具/人工来源、运行回执与全部问题。缺陷进入原群讨论，软件代码判断仍需 P4 真实调查回执；明确解决方案并逐人确认修订计划后，再由责任人执行修复，发布新候选并运行相关回归。第二次失败继续第三轮，不以“建议修改”收尾。

验收方法、范围或测试命令变化需要明确提案；一致同意更新范围/用例/计划，异议由 P3 裁决。审查工具不能通过删除断言刷绿。修改内容使旧证据失效，修改需求/团队/验证基线使旧签字失效。人工结论只在本次用户答复产生的需求基线、原验收方法/能力、原工作项职责依赖及同字节候选下保留；后续新输入不能沿用旧人工结论。

文档审查需完整读取正文或实际格式解析，记录专业问题再修订复审。需要联网来源核验而当前审查工具未接通时明确阻塞，不能编造调研来源。真实浏览器、命令或专业能力缺失/失败均回 P3；不自动安装、不借其他模型冒名测试。新增环境或访问继续使用已有审批边界。

## 用户处置、逐员认可与完成入口

用户可以自由建议、补条件、明确人工验收、明确豁免或暂缓指定项。选择“我承担本次测试或审查”只是责任安排，不表示已经通过；候选制作后仍逐项等待具体用户验收。用户回执写入 `source=human`、`actorId=user` 的 P6 报告及用户身份消息，保留 manual/waived 状态与 P3 responseRef，不伪造自动运行。豁免在交付气泡明确标记。

deferred 项及其依赖暂缓，其他已确认独立工作继续。只有这些工作真正做完且根任务暂停后，P3 `remainderReady` 再次提醒；不能因空工作项、材料交接或出版检查点提前收尾，不能把暂缓等同 pass/waived。还有 deferred 时禁止正式完成。

进入 reviewing 后，P4 加载实际候选 manifest 与有效报告，对当前团队每位成员分别使用自己的配置与身份请求明确认可。签字绑定需求、团队、验证版本、iteration 和摘要；响应中的假 memberId 不被接纳，失败、沉默和协调者概括不是签字。一人反对即阻止交付，保留异议及 P3 裁决入口；成员失效保留原责任并重新确认，不能隐式剔除。

正式完成必须同时满足：无未决有效异议、无待决/暂缓事项、验收通过或明确人工/豁免、当前团队全员当前版本认可、没有待纳入输入、实际候选及报告仍有效。最后重新核对成员资格、模型与凭据可用性。

**全部完成路径审计结果：**

| 路径 | 群 v2 行为 |
| --- | --- |
| loop explicit finish | 返回 workItemCompleted 和 stepCompleted，只完成当前工作项；不写根 completed |
| loop handoff | 经同一 finish 校验门槛转换为工作项信号；不能跳过审查或推进旧 handoff |
| single artifact 自动完成 | v2 门禁关闭；保留旧任务兼容路径 |
| runner execute / final response | 材料、制作与审查保存交接或报告；不发送 legacy 最终回复，不写 completed |
| 制作完出版 / 出版失败重试 | 冻结或找回同 publicationId 候选；排队送测，不宣告整个目标完成 |
| candidate/review 附件 notice 重发 | 只重发原冻结文件及原作者报告；成功后继续本轮状态，不跳过验收 |
| 正式交付 | runner 先记录 v2DeliveryPrepared；coordinator 串行入口检查 FIFO/版本，核验证据、封存与投递，然后唯一写 completed |
| final 附件投递失败重发 | 仅原封存文件重发；不调用模型、不新建候选、不重开开发；v2CompletionRecorded 防重复 completed 事件 |
| legacy handoff / legacy附件完成 | v2 分支提前隔离；原普通/私聊/旧群任务行为继续回归 |

正式封存发生在 coordinator 的同一串行完成边界内。输入在进入串行 FIFO 前先登记到达标记；封存前、封存后与附件发送后再次检查，防止投递 await 期间的输入排在 completed 后才被看见。若新输入在发送过程中到达，原文件仍保留，消息改为“本轮已封存，新增输入待处理，任务未正式完成”，不产生 completed。标记只是当前进程的到达屏障，原文与附件仍由现有持久 FIFO 保存，不是第二队列；进程崩溃恢复整体由 P8 验证。

验收已封存而仅附件复制失败时，记录“验收已通过／投递失败”、可重试 failure 与 resumeRequired。其重发使用原 producer 和已封存字节，不依赖后来角色凭据或重新签字。验收、投递、任务输入状态各自真实呈现。

群聊天显示成员问题回应、材料交接、候选送测、审查报告、修订及每位认可；长方案、全部缺陷和回执通过可打开 JSON 附件查看。面板显示当前责任人、工作项状态/结果引用、候选与摘要、验收状态/版本/证据、逐成员同意或异议，以及过期签字“已失效”。没有只发“大家已完成”或截断问题协议。
