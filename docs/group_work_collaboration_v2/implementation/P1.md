# P1 实施记录：协作状态与确定性门槛

日期：2026-09-30。范围仅为 v2 状态、版本门槛、受控增量入口、上下文与备份兼容。普通群任务仍创建 v1；P2–P8 和真实协作闭环尚未上线。

## 实际数据形状与权威边界

唯一权威业务状态位于 `AgentTask.executionStateJson.discussionState`。该子状态 `schemaVersion: 2` 保留既有讨论壳，并增加 `collaboration`：

```text
collaboration:
  taskId, conversationId, projectScopeId, revision
  requestRevision, teamRevision, verificationRevision
  requestMessageId, scope, plan, coordinatorId, phase
  artifactContract: type, format, location, revisionTarget
  team[]: memberId, role, qualificationRef, qualified, available
  workItems[]: id, ownerId, dependencies[], status, requestRevision
  issues[]: id, sourceId, kind, status, target, problem, evidenceRef,
            resolution, resolutionRef, retestCondition, requestRevision
  acceptances[]: id, method, requiredCapability, status,
                 evidenceRef, requestRevision, verificationRevision
  iterations[]: id, artifactDigest, requestRevision, teamRevision,
                manifestRef, reviewRef, status
  approvals[]: eventId, memberId, kind, subjectId,
               requestRevision, teamRevision, iterationId,
               artifactDigest, verificationRevision, approved,
               evidenceRef, source
  decisions[]: id, revision, status, reason, answer, impact, responseRef
  pendingInputIds[], appliedEventIds[]
```

列表和文本有界，嵌套字段按白名单校验。正文、测试日志和历史文件不放入此根检查点，只存 ID／索引。`WorkContextSnapshot` 和提示压缩保留 v2 状态作为只读摘要来源；增量只从任务的 `executionStateJson` 读取并写回。v2 当前不使用旧讨论的 `understandingPercent` 放行。

方案门槛要求当前范围、明确方案、产物合同、验收项、有效团队、已处理问题／决策、无待纳入输入，以及每名成员对相同需求／团队／验证版本的明确方案认可。交付门槛另要求当前候选迭代的清单和审查引用、对应版本验收证据，以及每名成员对同一 `taskId + requestRevision + teamRevision + iterationId + artifactDigest + verificationRevision` 的认可。空团队、多数票、缺席、最后一次反对意见、旧签字均不放行。

`defect` 须解决或由用户明确豁免；`idea` 纳入须全员明确同意或有用户裁决，拒绝提案也须有用户裁决；`deferred` 始终阻塞受影响门槛，`waived` 保留未验证语义并要求用户回应引用。普通“继续”不会改成 `passed`。`manual` 与 `passed` 分列，均需证据引用。

## 兼容与改动入口

- `WorkDiscussionState.initial` 仍建立 v1；`tryParse` 分别严格解码 v1/v2。`fromLegacyTask` 是显式、保守的未完成任务转换：旧百分比、旧 handoff 和旧完成结论不转成签字；旧已完成任务不转换。未做启动批量迁移。
- v2 暂不进入旧单执行者 runner，旧讨论 runner 也不消费 v2。协调器新增 `applyCollaborationUpdate` 受控入口，校验 task/conversation、来源角色和成员身份、`expectedRevision`、版本单调性、允许修改的字段；同一事件重放不追加认可。v1 的 `updateDiscussionState` 不可覆盖 v2。
- `mergeIntoExecutionState` 拒绝以 v2 覆盖坏 JSON、未知子状态或未知根检查点；更新现有 v2 必须提供预期协作版本。根 `schemaVersion` 与 `discussionState.schemaVersion` 独立校验。DM 的讨论判据保持原样。
- 只靠上面那道守卫不够：追问推广与「从头开始」重试都**先清空**执行检查点再写回 `_renewDiscussionForRequest` 的 v1 状态，那时守卫已经看不到上一份 v2 状态，协作记录会静默消失。因此三处旧入口各自在**改动之前**拒绝 v2：`_renewDiscussionForRequest` 抛错（兜住所有调用方）、重试路径抛错、追问推广按讨论等待暂停；`_carriesV2Collaboration` 是唯一判据。
- 备份仅携带上述白名单业务字段；本机绝对产物位置丢弃，`projectScopeId` 变为 `portable-unbound`，成员标为不可用，验收／候选的本地证据文件引用清除并递增团队和验证版本。审批权限、锁、可信本地工具结果不出口。`copyWithNewIds` 重写嵌套 task、conversation、member、message 引用；导入后仍阻塞待核对。交付文件本体的完整备份在 P6/P8 完成。

改动集中在 `work_discussion_state.dart`、`work_collaboration_state.dart`／`work_collaboration_state_gate.dart`、`work_task_coordinator_submission.dart`、讨论启动防线、备份 codec 与 restore 重写。没有新增 Hive 字段、`@JsonSerializable` 或生成文件，因此本阶段无需运行 `build_runner`。
