# 产品与技术设计

日期：2026-09-30。已确认业务决定见 [README](README.md)。下文的状态字段、目录样式和诊断阈值是实现方案，不是新增用户限制。

## 1. 目标、边界与必须承认的代价

工作模式提供一个围绕任务的工作团队：成员理解目标，带证据提出和回答问题，形成可执行方案，制作成果，独立审查，修订，并共同认可最终交付。公开群聊承载协作事实，任务面板承载状态与证据索引，文件承载实际成果。

“全员认可”“自动采纳一致同意的新想法”“不限制总步数和时长”是本次明确选择。它们可能增加时间、费用和范围，不能承诺任务一定在有限时间内完成。系统必须可观察、可停止、可恢复；持续争执或重复失败应把实际问题交给用户，不能偷偷改为多数票或恢复累计上限。

取消的是累计业务限制，不取消用户已经配置的费用／请求治理、单次调用超时、目录权限、危险命令审批、模型上下文窗口、解析与文件大小保护。触发这些约束时必须准确说明原因，不再笼统显示“任务超时”。

默认采用同一任务内串行的成员动作，不新增多成员同时写同一工作区。多人协作体现在各自负责、真实交接和反馈；不以并行执行数量作为目标。保留 App 级现有并发调度。

只针对“交付软件”的任务强制开发闭环。要求“写一份 HTML 游戏需求文档”时，交付对象仍是文档，不能因为出现 HTML 关键词就擅自进入游戏开发。团队提出扩展想法时须走已确认的新增范围规则。

## 2. 用户看见的流程

~~~mermaid
flowchart TD
    A[提出任务与附件] --> B[选择相关团队与协调成员]
    B --> C[需求梳理与资料查证]
    C --> D{已知疑问解决且完整方案确认}
    D -- 否 --> C
    D -- 是 --> E[按职责制作成果]
    E --> F[保存本轮候选交付文件]
    F --> G[测试或专业审查]
    G --> H[结果带回群聊]
    H --> I{有效异议或验收未通过}
    I -- 是 --> J[定位问题并确定修订方案]
    J --> E
    I -- 否 --> K[当前团队逐人确认同一版本]
    K -- 有新问题 --> H
    K -- 全员认可 --> L[正式交付该版本]
    C -. 需用户决策 .-> U[持久化弹窗问题]
    H -. 需用户决策 .-> U
    U --> V[选择方案或自由输入建议]
    V --> C
    V --> W[暂缓指定项并推进不依赖工作]
    W --> X[其他工作完成后再次提醒]
    X --> U
~~~

图中的环不是固定聊天轮次。每次只调度能够回答当前问题、执行当前工作或验证当前成果的成员。可以一次查证就解决问题，也可以多次修订；不会为了“至少两轮”追加废话，也不会因超过六轮而截断。

### 2.1 软件任务的必经内容

1. 需求梳理：目标、玩法／业务规则、用户场景、边界、交付形式和验收项。
2. 技术确认：开发实际检查相关代码或环境，说明可行性、修改位置、依赖与风险；测试参与确认异常、边界和可执行的测试方案。
3. 方案确认：全部已知疑问有答案、明确取舍或用户明确处置；团队自主确认，无需例行等待用户批准开工。
4. 实现：由具备能力的成员生成／修改软件，工作区有真实产物。
5. 送测：保存候选版本与需求、测试用例等必要文件。
6. 测试：按当前验收项实际运行；测试结果绑定该候选版本，不以阅读源码替代要求中的运行验证。
7. 问题讨论和返工：测试报告进入群聊；成员定位原因、确定修复，开发修改，测试复测并检查受影响回归。
8. 团队复核与正式交付：所有当前团队成员明确认可同一版本；提供最终文件和验收结果。

“先确认再制作”不禁止需求阶段读代码、搜索资料或查看已有证据，但默认不允许尚未确认方案就写原型来替代讨论。确需实验性修改解决技术未知项时，提出具体调查方案，由用户决定是否例外授权；不能把写代码动作伪装成只读调查。

需求文档、技术结论、测试用例的详细程度随任务规模调整。小软件可以用一份清晰的工作说明承载三者，不强制生成三本长文档；这些内容必须实际存在，不能只留一句“已完成设计”。

### 2.2 非软件任务

| 类型 | 制作与审查要点 | 不能冒充的证据 |
|---|---|---|
| 文档 | 内容范围、事实／逻辑、结构、格式、能否打开、指定位置 | 文件头合格不等于正文满足需求 |
| 调研 | 来源与日期、论点对应证据、矛盾信息、结论边界 | 多个角色重复同一说法不等于多来源验证 |
| 设计 | 尺寸／格式、交互或视觉要求、实际产物查看、使用场景 | 描述了设计不等于生成了设计文件 |
| 数据处理 | 输入范围、计算方法、输出结构、抽样／总量核对 | 程序退出码 0 不等于计算正确 |
| 其他 | 围绕具体目标形成制作责任与可验证审查项 | 无对应工具时不得声称已验证 |

通用流程只统一问题、工作、证据、版本与认可；不为每一种任务建立一套独立引擎。每次实际交付都有文件；简单文字成果可以是一份短文档，不额外制作无意义的附件集合。

## 3. 团队、权限与一致同意

### 3.1 参与者

- 从当前群成员中按任务所需能力选择工作团队，记录选择理由与责任。协调职责可由团队内合适成员兼任，不新增虚拟经理。
- 协调者负责提出下一步、组织讨论和索取确认，不拥有替其他成员发言／批准的权限。
- 每个角色使用自己的模型配置、身份、能力与记忆；不能用协调者模型一次编造全队对话。
- 软件测试责任应由不同于该版本主要实现者的合格成员承担；缺人则按 D16 请求补充或由用户承担对应验收，不凭空制造第二人格自测。
- 缺少必要角色时列出已有角色库中的候选、资格、可用模型与工具条件，由用户确认加入**本次任务**。默认不修改群的永久成员名单；参与者读取任务所需共享材料，不因此获得群外私人历史。
- 非工作团队成员提出有效问题时也应处理；他们不会因补充一句意见自动成为必需签字人。
- 已进入团队的成员掉线、删除或变得不可用，不能当作默许，也不能为了获得一致意见偷偷踢出。补人／替换走用户决策，递增团队版本并重新核对受影响责任。

### 3.2 同意的对象

至少记录两类明确意见：对当前方案的认可，以及对当前候选交付的认可。新增范围还要有针对该提案的逐成员同意记录。

正式交付认可绑定：

~~~text
taskId + requestRevision + teamRevision
+ iterationId + artifactDigest + verificationRevision
~~~

- 每名成员必须有自己的模型响应或真实人工回应凭据；沉默、请求失败、空输出、弃权和协调者总结都不算认可。
- 每条认可说明已审阅的责任范围和依据，不要求所有角色亲自重复运行全部测试。
- 任一有效版本要素变化，旧认可保留为历史，但不再满足当前交付。未改变的测试证据可以按依赖复用，但团队需对新版本重新明确认可。
- 团队为空、角色身份不匹配、成员资格失效时，不能利用“空集合全通过”完成任务。
- 请求格式、内容和文件结构校验通过只是候选送审条件，不能直接把整个群任务置为 completed。

### 3.3 异议、新想法和豁免

有效异议至少含：关联目标／需求／验收项、具体问题、依据、期望结果、解决或复测条件。证据可为工具结果、代码位置、来源、可复现步骤或明确的需求矛盾；不必先跑出错误才能提出合理的风险问题。

所有成立的质量异议都必须解决或由用户明确处置，不仅是“严重缺陷”。严重程度只影响处理次序。没有依据的偏好先作为建议，协调者要求澄清，不能直接删除他人的异议；是否成立仍有争议时由用户裁决。

范围内正常实现取舍由团队处理。范围外的新想法全员明确同意后可纳入，保存提案、同意记录、影响与新需求版本，更新测试和角色需求。不能因此覆盖用户明确的禁止项、强制格式、指定修订路径，也不能代替命令、目录、安装或网络访问授权。存在分歧时弹窗，不允许多数票强行采纳。

用户明确豁免某验收项时记录原项、原因、适用版本与未验证风险，标为 waived，不标为 passed；更新验收基线，再收集成员对该基线下交付的认可。“先继续”“其他先做”只表示 deferred，永远不能推导为豁免。用户人工验证提供的结果标明 manual，不能伪装成自动测试日志。

## 4. 讨论必须解决问题，聊天可以自然

### 4.1 发言与行动

讨论的基本单位是“待回答问题或待完成工作”，不是“某人贡献一条建议”。成员可提出问题、回应某人、报告查证结果、指出矛盾、请求调查、提出方案、明确认可或发起异议。

去掉所有成员统一的“职责意见：”“我建议……”前缀、强制理解百分比和合同 JSON 正文。内部继续使用可校验协议，但只把成员自然的公开表达写入气泡；协议状态与工具参数进入任务状态／详情，不要求用户阅读。

不增加一个专门模型把每条发言再次改写成口语，以免重复成本、误改结论或冒充角色。由当前成员在一次响应内生成公开表达与结构化增量；程序分别校验和呈现。协议失败时保留可安全展示的失败说明，但不能从一段预览文字中推断签字、解决问题或开工。

上下文至少提供：任务目标、当前需求版本、团队分工、当前问题、相关事实／工具证据、最近相关对话、该成员的个人上下文。其他成员的话是待核实信息，不能提升为用户指令或工具授权。

### 4.1.1 公开发言质量：核心验收要求

工作群应像真实同事围绕具体问题交流。自然发言是本次重构的核心要求，不能以“流程已经跑通”代替验收；适用于需求讨论、调查反馈、技术确认、测试异议、修订交接与最终认可。

- 普通讨论默认一到三个短句，一次围绕一个主要问题；简短确认可以更短。复杂取舍确需解释时可以展开，不设机械字数截断，也不为凑句数拆消息。
- 直接接住别人具体的问题，提供本轮新增信息、判断或下一步。不要每人重述任务背景、重复完整需求、轮流提交一份完整方案；建议要具体到当前对象，必要时说明理由，但不强制“结论—依据—行动”三段式。
- 不强制职业前缀、自我介绍、标题、编号、固定开场或收尾；避免只有“提升体验、增强稳定性”等空话。职业通过关注的问题体现，性格通过措辞、直接程度和讨论习惯体现。
- 可以不同意、追问、承认不确定、更正先前判断。不能为了像真人强塞语气词、表情、玩笑、舞台动作或制造争吵；不得编造读代码、测试结果与个人经历。
- 没有新增信息且无待履行责任时可以不发言。直接提问、未决异议与必须的逐成员认可仍需真实回应；不能用去重或“少说话”省略签字，也不能由协调者代答。
- 协调成员只在需要收敛问题、做决定或交接时总结，重点说变化、分歧和下一步，不在每条发言后重新概括全组意见。
- 完整需求、代码、测试用例、日志和缺陷明细进入对应文件或可查看详情；气泡说明关键发现及实际证据入口。一次检查仍须完整收集范围内全部问题，不能把“短发言”误解为只查或只记录一个问题。

表达对照（只示意质量，不作为所有任务复用的话术）：

> 不合格：作为测试工程师，我建议从功能性、稳定性、兼容性等维度全面测试，确保良好的用户体验。
>
> 合格的待验证建议：掷骰子按钮连点时会不会走两次？移动过程中可能需要禁用按钮，我先查这个。
>
> 合格的查证后反馈：确实会多走一次，我复现了。移动结束前先禁用按钮，复现步骤在本轮报告里。
>
> 开发接话：那我加一个移动中的状态，修完请你按同样步骤复测。

查证后反馈必须有真实工具证据和可打开的报告；没有执行就只能表达待验证判断，不能照抄示例声称已复现。

实施必须检查实际生产提示、上下文选择、协调总结与消息拼接的完整路径，清理相互冲突的长报告要求。公开表达与内部结构化状态分别处理；不得靠降低整个协议的输出预算、截取前 N 字、机械拆成多条气泡或仅折叠界面冒充优化。必要长内容保留完整且可查看，不额外启动逐条模型润色服务，不因风格不够短无限重试或丢弃有效证据／认可。

### 4.2 调查能力

需求讨论允许实际使用已有 `workspace.list/read/search`、附件解析以及已获准的搜索能力。工具入口必须检查当前阶段能力，不仅在提示词里写“只读”。

任意 `command.run` 不因为名字里有 read、test 或 analyze 就视为无副作用。只读调查优先用受控文件工具；确需命令、安装、运行项目或写探针，进入现有审批与明确工作项，不能绕过尚未确认方案的边界。

复用唯一 `WorkAgentLoop` 的有限调查动作与工具注册，不在 `WorkDiscussionRunner` 里手写第二套工具 while 循环。协调器调度“某成员调查问题”，工具结果回到问题台账与公开讨论，然后再选择下一成员。每次调用带 taskId、成员、需求版本与问题／工作项 ID，迟到结果不得覆盖新版本结论。

取消当前针对特定样例项目的 dossier 硬编码推断；项目概况只做导航，代码判断必须来自授权范围内真实读取的证据。

自然聊天示例（不是固定话术，代码路径和测试结果必须真实）：

> 前端：我看了当前移动逻辑，终点判断在移动之前。这里会影响超出终点的处理，先把规则定下来。
>
> 测试：那要区分“必须刚好到终点”和“多余步数后退”。确定后我把边界用例加上。
>
> 协调成员：目前没有其他规则依据，这个选择会改变玩法。请用户决定，再继续实现。

每次发言不必长，也不必固定称呼或段落。没有新信息的成员可以不发言，直到其责任需要响应；最终认可阶段仍须逐人明确回应。

### 4.3 取代“理解 100%”

开工门槛使用可检查清单：目标与范围明确、产物合同明确、当前全部已知疑问已经解决／明确处置、方案确定、验收项定义完毕、所需能力与权限状态已知、团队对当前方案认可。

不再用模型自报百分比推动状态。界面显示“还有哪些问题待解决”“方案已确认”，而非声称达到客观的 100% 理解。历史百分比可保留展示，不能成为 v2 执行条件。团队未知的未来问题无法事先穷尽，出现时回到讨论。

## 5. 持久状态与现有引擎的接入

### 5.1 唯一任务，少量结构化记录

`AgentTask` 继续作为一个用户任务的根记录。优先升级既有 `executionStateJson.discussionState` 为 schema v2，沿用已建立的序列化、校验和上下文链路；不另造一个与之并行可写的工作流状态。名称可以在必要时局部调整，但迁移后必须只有一份权威业务状态。

核心字段建议如下。记录类型可按真实职责拆文件，不能为每一行再建服务、仓储和接口。

| 状态 | 最少需要保存的内容 |
|---|---|
| 任务基线 | schemaVersion、task/conversation 归属、projectScopeId、requestRevision、原请求引用、当前范围与产物合同 |
| 团队 | teamRevision、成员与职责、协调者、当前动作执行者、成员加入依据 |
| 阶段／工作项 | 当前业务阶段，工作项 ID、负责成员、依赖、状态、适用需求版本 |
| 问题／提案 | ID、来源、问题分类、关联需求、状态、解决依据；范围提案的逐人意见 |
| 验收 | 验收项、方法、必要能力、状态、证据引用与适用版本 |
| 候选迭代 | iterationId、需求／团队版本、文件清单与摘要哈希、审查结果引用、当前迭代状态 |
| 明确认可 | 成员 ID、方案／交付／提案对象、版本、结论、响应来源 |
| 待用户决策 | decisionId、revision、原因、备选方案、影响、用户建议、deferred／answered 状态、提醒记录 |
| 执行检查点 | 复用既有工具意图、审批、幂等键、文件证据、待处理输入；加入 stage/workItem/revision 归属 |
| 进展 | 最近有证据的进展、重复失败指纹、无进展窗口；不存私有推理 |

需求与团队版本必须单调递增。历史文件与事件保存在现有受管文件／事件目录，根检查点只保存当前必要状态和索引；不能每次把所有测试日志和历史全文塞进 JSON、消息或模型上下文。

### 5.2 状态推进

建议业务阶段为 `forming → clarifying → ready → producing → verifying → reviewing → delivered`，失败返工回到 clarifying 或 producing。`awaitingDecision`、`deferred`、`stalled` 是问题／工作项状态，不必全部扩展成 Hive 全局枚举。

继续使用 `AgentTaskStatus` 表示调度状态；业务阶段和“是否占用运行槽”分开。团队正在等待用户但还有已确认的独立工作时可以继续这些工作；全部可运行工作耗尽才释放运行槽并等待。保留会话任务所有权，不能让新任务越过未结束任务。

现有接入点的必要调整：

- `WorkRoleRouter` 负责团队资格与动作责任映射，不能再把“最终负责人”固定为全流程唯一干活者。显式指定成员和实际执行职责分开记录，不忽略用户指定。
- `WorkDiscussionRunner` 负责自然对话、问题增量和下一步请求；状态决定由协调器校验后提交，模型不能直接完成任务。
- `WorkAgentLoop` 继续执行所有真实工具动作，注入当前成员、阶段允许能力、适用基线及完成条件。
- `WorkAgentLoopResult`／runner 交接区分“当前工作项完成”和“整个任务完成”。制作成功产生候选文件后进入验证，不能先发布 completed 再偷偷改回 running。
- `_advanceCompletedHandoff` 不能只删除群讨论 early return 就算接通。旧链条的终态、预算、交付通知、身份和发送者假设都必须核对。v2 从同一权威状态派发后续动作，旧 `WorkHandoffState` 只用于兼容转换或只读投影，不与新状态竞争推进。
- 每次成员切换刷新模型、凭据解析、角色记忆、技能、工具权限与动作资格，不能复用上一人的上下文或签字。
- 唯一正式完成入口检查当前验收、全体认可、未决／暂缓事项、文件一致性和所有待纳入输入。任何生产路径绕过该入口都视为缺陷。

### 5.3 长任务和安全点

群任务累计动作数、执行时长只用于观测，不参与 v2 中止判定；不是把 100 改成 1000，也不是每次悄悄重置计数继续伪装有上限。全局私聊限制保持原语义。

讨论同样取消最低两轮、启发式 2/4/6 轮和每任务 96 次调用硬截止。可以按小批动作让出调度权并自动续调，但批次结束不能变成等待用户的业务暂停或隐形总预算。

下列情况仍须可检测：

| 情况 | 处理 |
|---|---|
| 单次请求无首字节／输出中断 | 按既有请求超时和有限重试处理，记录准确失败类型 |
| 同一工具输入和环境下重复相同错误 | 有限重试后标为 stalled，列出尝试与缺少的条件 |
| 多次讨论只换说法、代码反复来回修改 | 根据问题状态、证据、文件／验收变化检测无进展，弹窗求助 |
| 正常产生新查证结果或完成工作 | 保存进展并继续，不因累计步数／时长暂停 |
| 等待用户或权限 | 不轮询模型，不计为“无进展动作”，保存状态并释放空闲执行资源 |
| 停止、删除、清除数据 | 沿既有取消与迟到写入闸门立即收敛，不能自动复活 |

建议首版诊断阈值集中在一个策略中：连续 3 次同指纹失败；或连续 8 个相关成员／工具结果没有可证明的任务推进。这里是可测试、可调的异常检测起点，不能用作任务总动作数或固定讨论轮数。新用户建议、条件变化或新的有效方案可开启新的恢复尝试，但不能仅因重新发送同一提示就清除失败历史。

模型的 `substantive_progress=true`、随机改文件、递增百分比不算充分证据。进展需关联实际待解决项：新读取且相关的事实、问题有依据地解决、工作项完成、验收状态改变、全员认可的范围变更等。阅读第九个有必要的代码文件不能因为“读了八次”被判死循环。

自动恢复现有 120 秒尝试上限需要单独审计：不能包住正常 v2 后续执行并在 120 秒杀掉健康任务。断网重连／单次请求仍可有边界，不得以“取消总时长”为由无限等待网络。

## 6. 用户弹窗、补充和延后

一个持久决策记录驱动群聊提示、任务面板和弹窗，不能各自维护一套 pending 判断。扩展现有 `WorkTaskClarification.isAnswerable` 与动作服务，保留现有跟进目标澄清功能。

弹窗展示：需要决定什么、当前事实、成员分歧、已尝试方法、可选方案及影响；支持自由文本、选择方案、暂缓指定项、补充环境／成员、明确豁免和停止。按钮按问题类型出现，不把所有按钮堆给每个问题。

自由建议先持久化，再反馈“已收到”；成员结合原问题理解建议并重新检查条件。建议没有解决问题时说明具体仍缺什么，不能机械重复原弹窗，也不能自动判定同意某种权限操作。

去重键为 taskId + decisionId + decisionRevision + reminderKind。同一问题重建页面、重试或重启不能反复弹；“其他可完成工作已全部完成”属于新的 remainderReady 提醒事件，即使第一次问题已看过也必须再弹一次。多个暂缓项可在同一个收尾弹窗列出。关闭弹窗只表示暂未作答。

当前群处于前台时展示对应弹窗；其他群的任务先保留待处理入口和群内提示，返回该任务时呈现，避免突然抢占正在处理的另一个任务。每个待决事项始终可从任务面板重新打开。

暂缓不能用于绕过首次开工的方案门槛：目标、核心规则或技术方案仍不明确时，不得自行制作。继续独立工作是指已有确认方案覆盖的工作；用户明确调整范围后，才按新基线判断可执行部分。

用户执行中补充：

1. 接收端立即落盘，保留消息／附件 ID、顺序和指向的任务。
2. 等当前不可分割工具动作结束并保存结果，到安全点处理；不强杀写入一半的文件。
3. 普通追问可根据事实回答；需求变更更新基线并使旧版决策／签字失效，回到必要的增量讨论。
4. 迟到的旧模型结果不进入新基线；已经实际发生的副作用必须记录为旧版事实，不能装作没有发生。
5. 同一文件修订仍修改用户指定原路径；新增脚本、素材等不受同名修订钉定影响。
6. 明确独立新任务按现有 FIFO 排队；不能把任何闲聊、问进度或附件都误合并成需求变更。
7. 任务正式完成前原子核对输入队列与基线，避免最后一条修改被完成事件抢先越过。

## 7. 文件版本、验证与交付

### 7.1 三种文件不要混淆

- 工作文件：用户授权工作区内的当前文件；修订按原路径执行。
- 回滚快照：既有 `WorkSnapshotService` 的操作前镜像，用来撤销，有保留／清理策略。
- 候选交付版本：每轮送测的只读文件副本及相关证据，必须能够在后续工作文件被改动后独立打开。不能借用可能被清理的回滚快照冒充历史交付。

复用现有产物筛选、真实格式校验、打包、媒体复制与附件卡片。为每轮候选增加明确迭代标识、清单和索引，不要求工作区是 Git 仓库，也不默认把整个仓库、依赖缓存或敏感文件复制进附件。

示意目录位于已有 App 管理的交付／媒体存储下，实际使用现有目录服务定位：

~~~text
<managed-deliveries>/<taskId>/r001/
  artifacts/            # 候选内容冻结后不再覆盖
  candidate.json        # 文件相对路径、哈希、需求与团队版本
  reviews/<attemptId>/  # 每次测试／审查追加独立证据
  outcome.json          # 本轮最终结论，完成后封存
~~~

冻结候选内容后，测试报告可以追加为新的 review 记录，但不能改变待测内容。出现修复即创建 r002。只有候选内容、验收结论和签字都齐全后才封存 outcome；封存记录不可覆写。每轮送测即展示“候选版”文件卡片，审查后展示本轮报告；最终版本再标“正式交付”。

复制和落盘采用 staging → 文件校验 → 原子发布 → 持久索引；中途崩溃可以识别未发布候选，不能发布一半就用于验收。相同发布动作重试不得增加一个假迭代。

代码／素材的完整性和打开方式属于产物合同。仅有差异文件但缺少运行必要文件，不能称为可独立打开的交付版本。大型项目可提供合同约定的完整包或明确依赖基线的可重建包，不承诺无上限复制；空间／包体限制触发时请求可行交付方式，不删除旧版来掩盖失败。

### 7.2 证据与复测

验收证据至少标记：方法、执行者、时间、工具／人工来源、适用候选摘要、需求／验收版本、结果和可查看的日志或报告。测试失败保留复现步骤、预期／实际、受影响项和必要环境信息，错误输出须脱敏。

从冻结候选副本或可核对相同内容的工作区执行验证；测试运行前后检查内容摘要，确认测试没有悄悄改写被签字的文件。测试所需临时目录与测试脚本可以另存，不能被执行成员偷偷修改为“总是通过”。

没有浏览器执行能力时，HTML 标签校验或打开浏览器成功不等于游戏交互测试通过。优先复用已安装且已授权的命令／浏览器测试能力；不可用则请求补充环境、人工验收或明确调整要求。现有 `browser.context` 枚举不是可用工具凭证。不得为绕过限制暗开任意 URL／网络访问。

单文件存在、基础格式正确或者模型 finish，都只能完成本工作项。`_completeValidatedSingleArtifactTask` 一类捷径在 v2 中必须转为候选送审。DOCX 检查仍复用现有 guard，但内容审查另有证据。

### 7.3 交付失败、保留和清理

文件成果合格但消息附件失败时，保留已经封存的版本与原发送角色，仅重试发送，不重新生成、重复修复或把开发人的附件冒充测试人的交付。验收通过状态与附件投递状态分开显示。

用户删除任务遵守现有真删除和迟到写入闸门；不自动删除已生成交付文件。删除群聊／附件或用户明确清理版本时，走对应数据生命周期入口，避免孤儿索引。磁盘不足必须明确报错，不能静默覆盖旧版本。

完整／会话备份要保留其范围内的交付文件、便携版本索引与公开审查记录；仅配置备份不包含任务交付历史。复用既有附件备份通道，未能打包的本地文件必须列为缺失，导入后不能把无文件的索引标成完整历史。

## 8. 成员记忆、性格与项目边界

复用 `AICharacter`、`MemoryContextSelector`、`PermanentMemory`、`ObservationEntry` 和现有关系状态。工作模式生产入口必须真的调用这些能力，不能只保留一个测试中运行的 wrapper。

每个成员的输入按以下职责分层：

1. 当前用户要求、任务基线和可验证事实。
2. 本项目相关的公开任务事实、方案与已验证历史成果。
3. 当前角色可见且相关的个人记忆、通用经验、用户稳定偏好。
4. 职业、性格、自定义设定，以及通过 `effectiveMood()` 取得的有效心情／关系。

层次表达优先级，不要求新增四个存储服务。自定义设定或历史记忆不能覆盖当前用户要求、权限和事实；心情不能给遗漏测试找理由。不要把每条职业发言都写成“我以前遇到过”，无真实记忆就不编造经历。

现有 selector 是按观察者全局检索，不具备项目隔离；不能直接把项目代码／规则永久写入全局记忆再期望提示词自动隔离。

最小实现建议：

- 任务状态携带稳定 projectScopeId，优先利用现有工作区身份；工作目录重新绑定为另一个项目时轮换 scope，不能沿用旧项目事实。实现时核对是否已有可复用绑定标识，再决定是否追加可空持久字段。
- 项目事实优先留在该 scope 的版本化任务记录、文件和证据索引中，按需读取；跨任务读取仍受当前会话／成员可见性约束，不能只因路径相同共享群外历史。
- 通用经验和稳定偏好经已有观察／记忆写入链路落入成员自己的永久记忆，保留来源消息／验证事件引用和去重键。未经验证的猜测、尚未解决的争议不自动固化为事实。
- 旧记录缺工作来源／作用域时，不能自动迁移成“可跨项目的已验证经验”。保留原有个人记忆行为；无法判断适用项目的旧项目断言不作为当前工作的事实依据。
- 如果现有记忆观察路径会从工作聊天自动抽取项目事实，必须为工作消息增加来源／作用域识别，或把该类事实留在项目上下文；不能一边新增正确写入入口，一边让旧观察器漏写全局。需要扩展记忆模型时只追加字段，并覆盖生成、备份、导入、审计、遗忘与删除。
- 只有参加／可见该事实的成员才形成个人经验，不能给没参与的人同步“亲身经历”。公共证据可共享，个人解释仍按各自观察者归属。
- 记忆归纳失败不改变交付是否成功；保存可重试的去重标记，不能在重启时反复写相同经验。
- 删除工作任务推进现有上下文分界线后，不能通过项目检索通道又把被排除的任务全文塞回来。用户明确保留的通用经验遵循现有记忆保留／遗忘规则，不被偷偷删除。

## 9. 恢复、兼容和上下文边界

- 任务由 App 级协调器持有，页面只订阅状态；不得用 widget 无限循环、rebuild 或 toast 驱动工作。
- 检查点持续写入，正常退出可做最后收尾，但不能假设进程被终止前一定有回调。重启从最后持久状态恢复。
- 可恢复工作核对任务版本、当前文件、权限、角色和动作收据后自动排队。等待用户建议、成员确认或审批的事项仍等待；用户主动暂停／停止绝不能自动恢复。
- 工具已经可能执行、但提交记录尚未落盘的动作属于 uncertain。核对文件后置条件或已有操作凭据；无法确认时求助，不能盲目重放安装、外部调用、删除等非幂等动作。
- 自动启动恢复与网络失败重试是不同原因，不能共用一个标记导致用户手动继续也继承自动重试时限。
- 恢复不绕过文件授权、审批指纹、资源锁、会话保留、待处理 FIFO、删除闸门和数据清理 barrier；文件被外部修改后，旧验证和签字失效。
- 当前状态用于持久恢复的完整数据，不得被用于模型提示的有损压缩结果覆盖。模型上下文保留当前目标、有效方案、未决项、当前迭代、证据索引及下一动作，其余历史按需查。
- 超过上下文窗口时沿既有 compactor 做分页／摘要，不能为了无限总步数无限塞历史，也不能截掉尚未解决的问题。
- v1 已完成任务保持历史完成，不补造团队签字。v1 未完成任务保留原文件、输入和审批信息，转换为 v2 待核对状态；不能把旧“100%”当作方案确认／QA 通过。迁移已知且核对成功的工作自动继续，缺决策／权限则等待。
- 未知／损坏 schema 失败关闭并保留原始恢复线索，不能回退空 Map 当作新任务。根执行检查点版本与 discussionState 子版本分别校验。
- 备份导入区别于同设备重启：不搬运可执行审批、资源锁、原机器绝对路径或可信本地工具结果。版本文件与报告可作历史展示；需执行时重新授权、绑定项目和核验。copyWithNewIds 必须重写嵌套角色／会话／任务／消息引用，不能带错签字身份。
- 非群任务继续走原路径，不能因旧数据意外带讨论字段而触发 v2。
