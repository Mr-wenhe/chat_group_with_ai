# 阶段 03 需求文档：聊天核心架构与性能

状态：草案  
目标版本：待定

## 1. 阶段目标

在不改变现有聊天体验的前提下，使普通聊天、自动聊天、流式回复和工作模式拥有清晰且可测试的状态边界；同时让长对话和大量会话下的启动、滚动、搜索与收件箱保持流畅。

## 2. 背景与问题

- `ChatRoomPage` 同时管理 UI、消息队列、计时器、自动聊天、流式请求、记忆、附件和 Agent 工具流程。
- `AgentRuntime` 同时承担协议解析、规划、工具执行、重试、持久化和结果交付。
- 消息 Box 整体打开，群聊/私聊收件箱会扫描大量消息并重复排序。
- 聊天室一次加载全部历史；房间内搜索也只针对已加载列表。
- 图片读取和 Base64 构造包含同步文件 IO，可能阻塞 UI isolate。

## 3. 用户价值

- 消息很多时进入会话和打开收件箱仍然快速。
- 自动聊天、工作模式和用户发送不会出现重复回复、状态卡死或错误互相影响。
- 流式生成可以可靠停止、恢复和重试。
- 搜索能覆盖完整历史，而不依赖一次加载全部消息。

## 4. 范围

### 必须包含

- 聊天会话状态模型和显式状态转换。
- 普通聊天、自动聊天、工作模式的并发互斥规则。
- ChatRoom UI 与业务 Controller 分离。
- AgentRuntime 按协议、执行、持久化和交付拆分。
- 消息分页/窗口加载。
- 收件箱会话摘要索引。
- 流式 UI 节流与附件处理异步化。
- 性能基线、回归指标和大数据 fixture。

### 本阶段不包含

- 改变 AI 角色选择策略或提示词风格。
- 全局搜索产品功能；阶段 06 实现，但本阶段提供索引/分页基础。
- 完整导入恢复；阶段 04。
- 更换 Hive 为服务器数据库。

## 5. 功能需求

### R03-01 会话状态一致性

会话至少区分：空闲、用户消息排队、普通生成、自动生成、工作任务、等待审批、停止中、失败、已释放。非法状态转换必须被拒绝或排队，不允许仅靠多个 bool 组合推断。

### R03-02 可取消与恢复

- 停止生成会取消网络订阅和后续自动轮次。
- 页面关闭后不再写 UI；允许已经确认需要持久化的结果安全收尾。
- 工作模式审批、超时和恢复遵循同一任务生命周期。

### R03-03 长历史分页

- 初次进入只加载最近一页。
- 向上滚动加载更早消息，保持滚动位置。
- 引用跳转和搜索命中未加载消息时能够定位并加载目标窗口。
- 分页期间新消息追加不会产生重复或顺序错乱。

### R03-04 收件箱性能

- 群聊和私聊列表不应每次扫描、分组并排序全部消息。
- 会话摘要包含 last message、unread/mention、更新时间等可增量更新字段。

### R03-05 附件处理

- 大图片读取、压缩和 Base64 转换不阻塞 UI。
- 原生端也有明确的单文件/单消息大小限制。
- 不支持或超限时在发送前提示，而不是请求阶段静默跳过。

## 6. 性能目标

以下数值为初始建议，评审时可调整：

- 100 个会话、5 万条消息：冷启动到首个可操作页面 P95 < 2.5 秒（基准设备待定义）。
- 打开含 1 万条消息的会话：首屏 P95 < 800 ms。
- 收件箱普通刷新 P95 < 100 ms。
- 流式输出期间保持 55 FPS 以上，避免每 token 全页面 rebuild。
- 单次初始加载消息不超过 50–100 条。

## 7. 验收标准

- [ ] ChatRoomPage 不再直接包含网络流订阅、计时策略和持久化编排的主体逻辑。
- [ ] 状态机测试覆盖用户发送、自动聊天、工作模式、停止、失败和页面关闭。
- [ ] 1 万条消息会话按页加载，引用跳转和新消息追加正确。
- [ ] 收件箱使用摘要索引，不在每次 build 扫描全量消息。
- [ ] 图片处理不使用 UI isolate 上的同步文件读取。
- [ ] 现有 449 项测试保持通过，关键体验无回归。
