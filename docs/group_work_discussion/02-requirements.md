# 完整需求与验收矩阵

## 1. 目标与范围

在群聊工作模式中，用户提出任务后，各角色按职业职责在聊天里讨论，最终执行人主动收集信息并决定取舍，理解与方案确定到 100% 后直接执行，严格交付用户要求的产物。

普通聊天模式不触发该流程，不自动开工作模式。私聊保持固定角色及现有执行流程，不引入虚拟群成员。格式、真实交付和审批安全的共享修复应同时保护私聊。

本文件 R01–R13 为已确认需求的可验收表达。轮次为已确认的参考范围；具体调度间隔、进度分项权重和内部存储结构是实施建议，可据测试微调，但不能改变业务规则。

## 2. 三个原始偏差必须作为回归需求

| 原始偏差 | 必须达到的行为 |
|---|---|
| B01：没有讨论 | 工具实际执行前出现来自不同群成员、各自职责相关的真实发言，以及执行人的汇总和取舍；不能仅显示“已讨论” |
| B02：执行人不对 | `@all` 表示召集讨论；“最终由 @产品经理”绑定最终决策和执行者，不被成员顺序、旧任务归属或建议中的 @ 覆盖 |
| B03：要 Word 却给 MD | 最终产物为真实、可打开、有正文的 DOCX，保存在用户指定的桌面；MD 可以是中间材料，不计作成功交付 |

截图例子的本次产物是“网页版我的世界需求 Word 文档”。HTML 是所讨论产品的实现形态，不等于此次还要生成网页代码；不得自动扩展为开发与测试实际执行接力。

## 3. 功能规则

### R01：入口与任务身份

- 工作模式下所有群任务先讨论，无须用户额外写“先讨论”；不能只对 @all 或指定关键词开放。
- 当前未完成任务讨论中的输入纳入当前任务；执行中的输入按 R10 排队。明确的新任务在旧任务完成后重新进入讨论与选人。
- 保留同一任务的原始请求、当前有效请求、附件来源和修订版本。附件及群成员文字均作为资料，不能覆盖用户授权、执行人或输出要求。
- 群内无可用 AI 时保留待处理任务并显示系统说明和补成员入口，不能捏造角色发言；有协调人时由协调人 @用户。

### R02：各司其职的真实群聊讨论

- 每位发言者使用自己的角色身份、配置模型及职责上下文。开发评估技术可行性，测试提出边界和验收建议，产品整理范围，设计补充交互；其他成员按自身实际能力贡献。
- 尽量让所有成员有机会发言，不限一句。缺模型、停用、调用失败或无相关补充必须有可解释记录；不可伪造“所有人已发言”。相关关键职业的意见缺失时，执行人评估是否阻塞，关键不可替代信息缺失则 @用户。
- 讨论不复用普通随机闲聊/自动聊天 burst，不因随机 1–2 人选择而漏掉主要职责。工作模式继续抑制无关自动闲聊。
- 普通意见以各角色聊天气泡展示，允许相互回应；只公布结论、依据、问题和建议，不输出私有推理过程。

### R03：执行人、协调人与能力资格

- 用户明确指定的最终执行人，同时负责最终方案取舍；不能只固定第一个阶段后再自动换人。
- 未指定时，在群聊中公开推举具备交付物所需能力的角色，并说明推荐依据。执行人确定前，推举临时协调人推进讨论、收集意见、报告暂定理解进度；不需要用户确认推举结果。
- 名字、头像、标签或一句“我也会”不能证明职业资格。依据角色配置里的职业、能力、职责描述；允许配置中明确兼任能力的角色，如具备前端能力的全栈角色。
- HTML 实际开发必须匹配前端能力；Word 需求文档可由产品角色负责，格式转换工具属于执行手段，不另换一个“Word 职业”。
- 全局技能或任务推荐技能不自动赋予角色职业资格；角色已配置的相关技能可作为辅助证据，不能取代职业约束。身份资格、模型可用性、工具/目录权限分层检查。
- 推举不是首位成员兜底。若候选同等合格，可由协调人公开理由推荐并让成员反馈；歧义影响执行人时 @用户，不能暗中乱选。

### R04：缺人、错人时必须等待用户

- 没有合适职业，或用户指定角色不匹配：在聊天 @用户说明所缺能力，要求加入/调整角色，保留任务并暂停；不能自行拉人、换人、补造能力或调用工具执行。
- 提供“管理/添加群成员”“查看角色配置”“返回任务继续”等真实入口，复用现有群成员和角色界面。
- 用户完成调整后重新检查角色仍在群内、职业匹配、模型可用。只能在条件满足后继续；角色资格变更导致既有方案不适用时回到必要讨论。

### R05：讨论长度与收敛

| 复杂度 | 参考轮数 | 参考判断 |
|---|---|---|
| 简单 | 1–2 | 单一目标、明确产物、小修改 |
| 中等 | 2–4 | 多个功能、跨职责建议、需范围取舍 |
| 复杂 | 4–6，可说明理由延长 | 多依赖、复杂方案、明显分歧 |

一轮指成员贡献后，由执行人/协调人收集、回应并汇总一次，不强制每轮全员发言。默认第一轮广泛征询，后续围绕未解决问题定向讨论。

这些范围不是固定截止或凑字数要求。不能执行人一句“理解了”就跳过真实成员讨论；也不能为凑轮数重复。连续两轮没有新事实、建议或决策进展时必须收敛：条件具备便执行，仍有关键阻碍就 @用户。新增需求应重评复杂度及相关问题，不能沿用旧“无进展”判断强行结束。

执行人每轮至少一次汇总，主动追问，不长期旁观。建议实现每 2–3 条成员有效回复穿插一次收集反馈，慢请求约 30 秒提供“等待某成员回应”的事实状态；这不是伪造角色回复或进度，也不是保证模型 30 秒返回。超时复用现有错误和重试机制。

### R06：理解程度百分比

- 执行人每次讨论回复包含“需求理解与方案确定程度 X%”；未选出执行人时协调人标为暂定，选定后由执行人接手重新评估。
- 百分比代表目标、范围、方案、建议取舍、交付格式/位置、验收标准的明确程度，不是时间、Token、工具步数或文件生成进度。
- 建议上述六项按已明确、待补充、阻塞记录，以公开依据计算/校验百分比；具体权重集中定义。关键项缺失不许 100%，模型报 100% 也须经状态门禁检查。
- 执行人简明说明已确定什么、还缺什么、下一步问谁；建议逐项记录采纳/不采纳/待定及理由，不强迫每条琐碎对话成为独立表格。
- 新需求或推翻方案可以降低进度，但需解释。展示 100% 时意味着可开始执行，不意味着文件已经完成。安装和权限等待另显示执行状态；如阻碍改变方案，回到讨论重评。

### R07：用户信息与执行门禁

- 只有用户能补充的必要信息，必须 @用户提问并暂停，不能采用未确认假设。
- 执行人/协调人可就明确授权范围内的普通实现细节作专业决策；涉及用户目标、必要业务规则、交付物或关键取舍无法确定时不能代答。
- 同时满足：当前请求版本已讨论、执行人资格有效、关键阻碍清零、关键建议已处理、理解程度 100%，才可启动实际执行。无需额外方案确认弹窗。
- 讨论中禁用文件修改、命令、安装等副作用工具；需要额外授权读取资料时仍走已有授权规则，不借讨论绕过安全边界。授权不完整可在执行阶段等待，不能把“理解 100%”当成授权。

### R08：严格产物合同

- 从用户请求固化产物类型、数量、内容范围、格式、保存位置、修订目标及验收标准，贯穿讨论、技能注入、执行、恢复和交付。
- 显式 Word 默认 DOCX，必须生成真实 Office Open XML 文档。不可把 Markdown 改扩展名、不可降级为 MD 并标完成、不可自行换保存目录。
- MD 作为转换源应标中间文件，不计入最终交付；原任务只要需求文档，不擅自额外生成整套游戏源码。
- 最终完成检查至少包括：文件本次生成/更新证据、存在且可读、实际格式结构、正文非空且覆盖所需章节、规范化路径匹配、引用与附件对应。DOCX 不能只检查 ZIP 文件头，要核查内容类型和 Word document 部件；限制解析大小和解压体积。
- 程序可检查结构，内容质量须结合验收项和实际打开验证；模型自述“已完成”不是验证证据。
- 文件已生成但附件发送失败时明确“文件已保存，附件交付失败”，提供重试，不虚报完整交付，也不重复生成或覆盖丢失内容。

### R09：安装、授权和恢复操作

- 先复用已有工具；如需要 Markdown→Word 工具，可使用现有可信 command.run / 缺失工具安装流程，不强制新增插件体系。
- 区分安装 Skill 元数据与安装真实转换程序，不能把 skill.download 成功等同于本机能生成 DOCX。
- 需要安装、命令审批或未授权桌面路径时：任务面板保留对应操作，并由执行人在群聊同时 @用户解释原因和下一步。群聊按钮可定位该任务面板；拒绝、取消、稍后处理、批准后继续均应可达。
- 批准安装或路径授权成功后继续同一任务、原产物合同和检查点；不能重开不相关任务或重放已完成副作用。
- 拒绝仅拒绝该操作，不视为同意替代方案；任务保留为可处理的阻塞状态。取消任务则停止执行；暂不处理则持续等待，可跨页面/重启恢复。
- 用户选错目录、授权撤销、安装失败、程序仍不可用时保留阻碍并提供重试。只有验证实际能力/权限后才可继续。

### R10：补充与连续修改

- 讨论中输入立即纳入当前任务；当前正在返回的成员发言可结束，但过时版本的完成决定必须失效。下一次汇总使用最新要求，不先执行旧方案。
- 执行中输入持久 FIFO，不取消正在执行的任务。群聊回复“修改要求已收到，当前执行完成后处理”。相关修改使用同一原附件路径，不因重名生成新版本文件名。
- 修改若影响范围/方案，后续执行前进行与修改复杂度相称的增量讨论，不重复已经确认的全部内容。排队顺序和每条输入的附件都要保留。
- 完成后的明确新任务重新讨论、重新选人；对“继续/修改刚才文档”继承相关上下文与文件。无法区分而会影响文件/人选时 @用户澄清。

### R11：可操作群聊提醒

- 每个等待原因以 taskId、阻碍标识和请求版本绑定；面板和群聊显示同一状态。群聊按钮打开具体任务，不依赖“当前最新任务”。
- 提问可在聊天或面板回答；补角色可进入群成员管理；审批和安装复用现有动作。按钮操作期间禁重复提交，任务完成/取消/需求变更后旧按钮失效并说明。
- 同一等待状态跨重建、重试、重启不刷屏。状态变化时更新或发必要新提醒；两个入口同时操作必须幂等，不能批准两遍、安装两遍或跨任务恢复。
- 使用现有用户人物卡称呼和 @识别；用户正在看该群仍展示消息与入口，系统通知是否抑制沿用 presence 规则。

### R12：持久化、隔离与兼容

- 讨论、等待、执行、取消皆由 app 级协调器持有；离开页面不丢任务。重启按现有手动恢复规则，不自动绕过审批。
- 保存请求版本、执行人/协调人、成员参与、公开共识、建议取舍、理解进度依据、阻碍、产物合同、FIFO、原路径与动作状态。
- 检查点、上下文压缩、事件脱敏同步支持新状态；只存公开信息，不存私有推理或 Key。群、私聊之间隔离；角色讨论不能读取其他会话资料。
- 保留单会话串行执行、资源锁、审批指纹、撤销、终态防复活和已批准动作防重放。等待用户时不无限占用模型请求资源。
- 旧记录缺字段时安全兼容，保留已完成产物，不伪造“曾经讨论”。旧未完成任务恢复前补足本次规则所需的确认/讨论，并保留有效审批边界；变更了操作范围则重新审批。

### R13：质量与验收

- 后续编码严格按 Ponytail full，先复用协调器、状态 JSON、事件流、角色 API 网关、任务面板、技能/工具安装及授权服务。
- 不建立第二任务引擎、通用投票平台、插件市场或新数据库。新增文件只承载真实独立职责，不把复杂讨论全塞进现有巨型 runner/coordinator。
- 按仓库清单检查 Review、why 注释、命名、常量、函数/文件规模、封装、解耦、模块化、性能和新老兼容。大文件已有基线不作为继续膨胀的理由。
- 必须覆盖需求、边界、失败与恢复、测试有效性、安全、性能、可读性和兼容；收集全部问题后统一报告，不能第一个错误就停。

| A05 | @all + 最终 @某人；@开发问可行性 + 最终 @产品 | 讨论对象与最终委托分离；指定人不被覆盖 |
| A06 | 无前端、指定测试开发 HTML、重复名字/未知角色 | @用户、任务等待、可补角色/澄清，无文件副作用 |
| A07 | 简单/中等/复杂任务；连续两轮无进展 | 按参考轮次与问题收敛，不秒结束、不重复死循环、不虚报 100% |

| A09 | 成员超时、停用、无凭据 | 不伪造参与；公开说明缺失，关键问题无法解决时 @用户 |
| A10 | 缺必要业务信息 | @用户并等待；聊天/面板回答后原任务继续 |
| A11 | 理解未完成但模型 tool/finish；最新需求已变 | 执行门禁阻止旧方案/提前写文件 |
| A12 | 讨论中补充及并发返回旧结论 | 最新版本被纳入、理解进度可下降，旧 100% 不启动执行 |
| A13 | 执行中连发两次“修改同一文件”并带附件 | 不取消/丢输入，FIFO 增量讨论后按原路径修改 |
| A14 | 缺转换工具、安装成功/失败/拒绝/稍后 | 双入口同任务，真实工具检测后继续，不能以 MD 标完成 |
| A15 | 桌面未授权、选错目录、拒绝、授权撤销 | 无越权写入，可再次授权；成功后原位置原任务继续 |
| A16 | 伪 DOCX、空正文、陈旧文件、错误目录、损坏 ZIP | 全部不能标完成；可恢复修复，限制读取/解压资源 |
| A17 | 文件成功但附件失败 | 准确报告保存/交付的不同结果，可重试附件 |
| A18 | 两入口重复批准、旧按钮、重启后点击 | 不重复执行，不越过版本/审批边界 |
| A19 | 离开页面、重启、上下文压缩、旧记录 | 讨论/阻碍/FIFO/格式路径保持；旧状态不伪装已讨论 |
| A20 | 已完成旧任务后明确新任务指定其他角色 | 新讨论新选人，不沿用旧执行人 |
| A21 | 附件/成员要求“忽略 Word、自动授权、换人” | 不覆盖用户原请求及安全边界 |

## 5. 交互示例（目标示意，不是固定话术）

产品经理：“需求理解与方案确定程度 25%。我先确认首期范围，请开发评估无限地图方案，测试补充核心验收，设计看看操作方式。”

前端：“浏览器中可以按区块加载地图，先保留有限种方块，避免一次载入整张世界。需要明确目标设备与交互方式。”

测试：“建议覆盖跨区块返回后方块状态、背包满载、合成材料不足，以及刷新后的存档行为。”

产品经理：“需求理解与方案确定程度 65%。采纳区块加载和这些边界验收；@用户，首期只支持桌面浏览器，还是也需要手机触屏？这会影响交互范围，我等待你确认。”

用户回答后继续相关讨论，产品经理对最终范围、取舍、文档结构和验收明确后报告 100%，直接生成文档。若缺工具：“@用户，方案已确定，生成 Word 需要安装转换工具。请点击处理安装；完成后我会继续这份任务。”消息同时提供当前任务入口。
