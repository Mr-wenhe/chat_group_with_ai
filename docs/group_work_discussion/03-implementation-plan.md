# 分阶段实施计划

状态：S1–S7 已实施并通过复审；S8 已执行自动化全链路、真实 DOCX、原生窗口启动和一轮真实群聊讨论，但精确工作任务闭环、原生授权/安装和 Word GUI 仍未检查，整体暂不可宣告通过。业务依据为 [完整需求](02-requirements.md)，偏差依据为 [定位报告](01-findings.md)。

## 1. 最小实现路线（Ponytail full）

保持一个 `WorkTaskCoordinator`，在原任务生命周期内增加群讨论阶段，再交给现有 `DefaultWorkTaskRunner` / `WorkAgentLoop`。讨论顺序调用每个角色自己的网关，执行期间仍只有一个最终执行人。采用小型领域状态和纯策略，复用 `AgentTask.executionStateJson`、`WorkTaskEvent.safeMetadata`、现有 Message 与面板动作。

优先避免新增 HiveType 和修改 Hive 枚举；新增 JSON 需一个编解码入口、版本和边界校验，并接入现有检查点白名单。若事实证明现有字段不可用，说明具体限制后选择最小模型扩展，不提前建通用事件溯源框架。

建议最小状态包含：phase、requestRevision、coordinatorId、executorId、participants/参与结果、round、stagnantRounds、理解分项和百分比、openQuestions、decisionSummary、deliverableContract、blocker/actionVersion。名称为设计建议，不强制创建同名文件或类。职责复用优先于字段堆积。

阶段流：选协调/执行人 → 讨论 ⇄ 等用户信息/补角色 → 准备执行 → 执行 ⇄ 安装/授权等待 → 校验交付 → 完成。取消及中断恢复作用于各阶段。理解程度与执行状态独立；讨论完成不等于审批完成。

## 3. 实现细节与边界

### 请求、角色与合同

先查共享提及解析器全部调用方，普通聊天 @all 行为不变。保留 UI 已选角色 ID（如存在）与文本语义的来源，防止再次仅用展开列表选首人。中文“由…执行/最后…输出”和英文最终委托都要有代表样本；无法确定必须请求澄清，不追求庞大的自然语言规则库。必要时复用既有短模型路由，结构化输出仍须本地校验角色 ID、资格、产物和用户原约束。

职业按角色配置明确能力匹配，禁止仅靠关键词在名字/全局技能中命中；无需本轮建设独立职业注册中心。最终产物为 Word PRD 时 HTML/测试等可能只是正文主题，不自动生成 product→development→testing 工具接力。

### 讨论调度与并发

讨论需要单会话协调权，不能另开页面定时器驱动。每个异步回复携带请求版本，落库前确认任务未取消且版本适用。优先顺序邀请未发言成员，后续按未决问题定向；使用现有超时、重试、Token 预算，新增讨论轮次常量与无进展判断。

执行人配置在开始、恢复与实际执行前再次验证。讨论不拿写文件的资源锁长期等待，执行阶段继续现有资源锁；不能通过释放会话控制权让新请求另起并发执行。成员模型失败不能被伪装成成员建议。

### 状态与可操作提醒

JSON 拓展不是任意 map：使用最小类型化编解码，对未知版本、无效百分比、缺 ID、过大摘要安全处理。检查 `work_agent_loop.dart` 持久字段白名单、checkpoint 合并和 context compression，避免新字段被洗掉。

群聊消息用稳定关联键映射任务和待处理动作，重放不会重复写消息。按钮只导航到现有面板也可满足要求，面板动作必须重新校验当前任务/版本。已批准操作范围变化时重新请求审批，不能让旧按钮授权新需求。

### Word 转换与完成门禁

优先复用已存在的 pandoc 安装建议和 command.run，不引入 DOCX SDK 或新插件服务。实施时先验证本机转换能力及命令策略；若现有安全策略阻止合法转换，做精确能力扩展，不能放宽全部命令。

统一交付合同门禁约束 finish 和最终消息：MD 源、零字节文件、旧文件、路径不符均不能代表完成。利用现有文档/ZIP 依赖验证结构，不建立完整 Office 渲染系统。真实打开检查在最终验收；自动测试检查结构、正文和路径。

检查旧 AgentRuntime 所有调用方及旧降级测试。生产路径先修共享业务边界，仍受支持的兼容调用应同步禁止未经允许降级；确认退役才能删代码，不能为了消除关键词做无关大重构。角色已保存 Skill 可能带旧降级说明，应由用户合同/安全门禁优先覆盖，不删除用户自定义 Skill。

## 4. 每阶段共同完成标准

1. 开始读取根 AGENTS.md、Ponytail、需求及当前步骤；检查工作区，保留他人改动。
2. 阅读相关入口和所有调用方，写清最小复用决定。只实现当前步骤，不顺手重构全仓。
3. 非平凡逻辑至少有能捕获真实回归的可运行检查，优先扩展已有 flutter_test；不得用字符串存在性测试替代行为验收。
4. 运行相关测试和 `flutter analyze --no-pub`；变更 Hive 或 provider 时按仓库要求运行生成器，禁止手改 `.g.dart`。
5. 按代码质量十项及完整性规则 review，发现问题继续检查其余范围，集中按严重性报告，列明未检查项。
6. 更新阶段记录：变更/原因、复用点、测试命令与结果、对应 A 编号、剩余风险、下一步。不自动提交、推送或发布。

## 5. 执行方式

S1–S4 使用 [详细提示词上篇](04-prompts-stages-1-4.md)，S5–S8 使用 [详细提示词下篇](05-prompts-stages-5-8.md)。可逐条复制给编码任务；每次只执行一个步骤，下一步骤读取前一步产物和测试结果，不重复需求访谈。

发生需求外歧义时保留已完成工作并只问一个必要问题；本次已确认的规则不得再次索要确认。遇到失败不得谎称阶段完成，且要继续不依赖失败项的检查。
