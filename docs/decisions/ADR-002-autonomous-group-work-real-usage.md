# ADR-002: 在现有执行循环内增加逐角色真实使用

## 状态与日期

Proposed，2026-10-13。用户已确认产品需求，本文记录建议架构；原生技术路线仍以 P0 现场验证为前提。

## 背景

现有群工作 v2 已有讨论、文件合同、候选冻结、审查、返工、认可、恢复及审批。新需求增加每个群成员对本轮产物的实际使用，并允许协调者自主决定一般分歧；优先 macOS `.app`，兼顾文档视觉质量、GitHub 技能和低打扰连续迭代。

只修改提示词无法补齐原生操作、渲染、技能资源、收据身份和完成门禁。直接替换外部多代理框架会同时引入第二套执行、状态与授权机制。

## 建议决策

1. 保留 `WorkTaskCoordinator` 和唯一 `WorkAgentLoop`。单制作执行者与多个试用角色分开；试用按当前角色身份串行复用执行循环。
2. 在候选和检查点内增加版本化使用计划及工具产生的收据引用。角色模型不能自行生成有效收据或代替成员签字。
3. 用已发布冻结产物建立隔离测试副本；macOS 应用包采用受控封装及包内身份核验，复用普通文件版本存储。
4. 原生操作优先验证 Appium Mac2；现有 Dio 负责窄范围协议适配，Appium/XCTest 负责实际 UI 自动化。工具适配器没有任务调度权。
5. 一般实现和审美分歧由协调者在授权范围内裁决，保留反对意见；真实必达项失败、用户明确约束、权限和能力缺失不能被裁决抹掉。
6. GitHub 技能按固定提交导入资源包，验证后激活，权限取交集。技能不改变职业资格、系统权限或当前已冻结验收。

## 替代方案

| 方案 | 取舍 |
|---|---|
| 仅加强提示词 | 改动少，但无法执行不存在的原生工具和渲染能力，无法保证逐角色真使用 |
| 完整换成 ChatDev/AutoGen/MAF | 有现成编排机制，但需跨运行时桥接、重做持久化和授权；尚无证据支持其为最小完整改动 |
| 自写所有平台 UI 引擎 | 覆盖自由，但校准、可访问性、系统兼容和恢复成本高，优先使用成熟平台工具 |
| 原生目录全部改为通用目录产物体系 | 更宽泛，但本阶段仅需 `.app`；先验证窄范围应用包封装与真实内层测试 |

## 后果

会新增必要的证据与权限边界、少量模型字段和原生/渲染适配器，并涉及备份恢复及真实硬件验收。不能把新字段塞入严格 JSON 后仅修改提示词；解析器、门禁、调用方、白名单与测试必须同步。

Mac2 需要本机依赖和系统授权，通用可操作性不能只靠单测证明。若 P0 在目标 App 上无法稳定操作，应记录实际失败并调整原生适配方案，保留现有主执行架构。

跨平台 runner 和多人并行制作留作后续决策。本 ADR 不改变现有凭据存储政策，也不授予发布、系统修改或跨设备执行权限。
