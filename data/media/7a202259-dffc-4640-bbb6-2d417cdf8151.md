## 一、严重问题 (Critical)

### 1. 未实现接口导致链接失败
**位置**: 头文件第 34-37 行

`getProcessCPUUsage()` 和 `getProcessMemoryUsage()` 在类中声明了公有接口，但整个文件中没有找到对应的实现定义。

**风险**: 如果用户调用这两个接口，会出现链接错误 (undefined reference)。

**建议**:
- 实现这两个函数
- 如果暂时不需要，应移除声明或标记为 deprecated

### 2. 未使用的私有函数声明
**位置**: 头文件第 41-42 行

`updateCPUTimes()` 和 `calculateCPUUsage()` 声明了但从未实现。

**风险**: 代码可维护性差，容易误导其他开发者。

**建议**: 移除未使用的声明，或实现相关逻辑。

### 3. 重复数据存储导致数据不一致
**位置**: 类成员变量 (第 62-73 行) vs PlatformData 结构体

类中定义了 `m_prevUser`, `m_prevNice` 等 CPU 采样成员，同时 `PlatformData` 结构体 (Linux 平台) 中也定义了相同的字段。

**关键问题**:
- `getCPUUsageLinux()` 只更新了 `PlatformData` 中的值
- `m_prev*` 成员变量只在构造函数中被初始化，之后从未更新
- 这导致数据重复且部分数据失效

**建议**:
- 删除类中的 `m_prev*` 成员变量，统一使用 `PlatformData` 管理
- 或删除 `PlatformData` 中的冗余字段，统一使用类成员

## 二、中等问题 (Major)

### 4. Const 正确性违规 (Const Cast)
**位置**: `getTotalMemory()`, `getUsedMemory()`, `getAvailableMemory()` (第 211-237 行)

三个 const 成员函数使用 `const_cast` 调用非 const 的 `getMemoryInfo*` 函数。

**风险**:
- 破坏了 const 语义
- 如果未来这些函数真的修改了对象状态，const 对象会被意外修改

**建议**:
- 将 `getMemoryInfo*` 函数声明为 `const`
- 或在类中缓存内存信息，避免每次调用都查询系统

### 5. 初始化状态管理错误
**位置**: 构造函数 (第 107-130 行)

`m_initialized` 在构造函数末尾无条件设置为 `true`，但 `initWindows()`/`initLinux()`/`initMacOS()` 可能失败（如 Windows 下 PDH 初始化失败）。

**风险**:
- 初始化失败后，`m_initialized` 仍为 true
- 后续调用 `getCPUUsage()` 等函数时，可能使用未正确初始化的平台数据

**建议**:
- init 函数应返回 bool 表示成功/失败
- 构造函数应根据 init 结果设置 `m_initialized`
- 或者在每个 getter 中检查平台数据是否有效

### 6. 线程安全缺失
**位置**: 整个类

类中没有使用任何互斥锁 (mutex) 或原子操作。

**风险**:
- 多线程同时调用 `getCPUUsage()` 会导致数据竞争
- 一个线程正在更新 `prevCpuInfo` 时，另一个线程读取它，会产生未定义行为

**建议**:
- 添加 `std::mutex` 保护平台数据访问
- 或使用原子操作 (atomic) 保护简单状态
- 考虑线程局部存储 (thread_local) 如果需要多线程独立采样

### 7. Windows 初始化中的阻塞调用
**位置**: `initWindows()` (第 140-152 行)

使用 `std::this_thread::sleep_for(std::chrono::milliseconds(100))` 阻塞线程 100ms。

**风险**:
- 构造函数阻塞时间过长
- 在实时系统或高性能场景下不适用

**建议**:
- 移除睡眠，使用第一次调用时延迟采样
- 或提供异步初始化接口

## 三、轻微问题 (Minor)

### 8. 代码冗余
**位置**: `getTotalMemory()`, `getUsedMemory()`, `getAvailableMemory()`

三个函数的实现几乎完全相同，只是返回值不同。

**建议**:
- 提取私有辅助函数 `queryMemory(uint64_t& total, uint64_t& available) const`
- 三个公有函数调用辅助函数后返回相应值

### 9. 可读性问题
**位置**: `getCPUUsageLinux()` (第 270-320 行)

变量 `idle` 被重载：先解析得到原始值，然后又 `uint64_t idle = idle + iowait;`。

**建议**:
- 使用 `idleRaw` 和 `idleTotal` 等更清晰的命名
- 或拆分计算步骤，添加注释

### 10. 错误处理不完善
**位置**: `getMemoryInfoMacOS()` (第 360-380 行)

如果 `sysctlbyname("hw.memsize", ...)` 失败，`total` 保持为 0。如果后续 `host_statistics64` 也失败，`available` 也保持为 0。

**风险**:
- `getMemoryUsage()` 中 `if (total == 0) return 0.0;` 会掩盖错误，返回 0% 使用率
- 调用者无法区分"内存为 0"和"查询失败"

**建议**:
- 设置 `m_error` 记录具体失败原因
- 考虑返回负值或特定错误码表示查询失败

### 11. 内存管理
**位置**: 构造函数/析构函数 (第 107-135 行)

使用 `void* m_platformData` 存储平台数据，通过 `new/delete` 管理。

**风险**:
- 类型不安全
- 如果构造函数在 `new` 之后、`init` 之前抛出异常，可能导致内存泄漏
- 析构函数中只处理了 Windows 的清理，其他平台虽然不需要特殊清理，但结构体分配的内存由 `delete data` 处理，如果未来 PlatformData 包含需要特殊清理的资源，容易遗漏

**建议**:
- 使用 `std::unique_ptr<PlatformData>` 管理生命周期
- 或至少使用具体类型指针 `PlatformData*`

## 四、设计建议

### 12. 平台抽象层设计
当前使用 `#if defined(...)` 条件编译分散在各个函数中。

**建议**:
- 使用策略模式 (Strategy Pattern)，为每个平台实现一个 `PlatformImpl` 接口
- 在构造函数中根据平台选择具体实现
- 这样主类代码更清晰，平台特定代码隔离在独立文件/类中

### 13. 首次采样策略
当前首次调用返回 0.0 或 -1.0，注释说"首次调用返回0.0或-1.0"。

**建议**:
- 统一首次采样行为，建议返回 0.0 并内部记录需要两次采样才能计算
- 或在文档中明确说明首次调用的返回值语义

1. **立即修复**: 实现缺失的 `getProcessCPUUsage()` 和 `getProcessMemoryUsage()`
2. **高优先级**: 修复重复数据存储问题，统一 CPU 采样数据管理

5. **中优先级**: 修复 const 正确性问题

// 将 getMemoryInfo* 声明为 const
void getMemoryInfoLinux(uint64_t& total, uint64_t& available) const;

// 或提取 const 辅助函数
void queryMemory(uint64_t& total, uint64_t& available) const {
#if defined(_WIN32)
    getMemoryInfoWindows(total, available);
#elif defined(__APPLE__)
    getMemoryInfoMacOS(total, available);
#else
    getMemoryInfoLinux(total, available);
#endif
}

uint64_t getTotalMemory() const {
    uint64_t total = 0, available = 0;
    queryMemory(total, available);
    return total;
}
